The phantom-table triage docs (`docs/qa/triage-*.md`) classify a table DEAD when no live HTTP entry point reaches the code that queries it — a mechanical, correct-as-far-as-it-goes reachability test. But "unreachable today" collapses two very different situations that call for opposite actions: (a) genuinely abandoned/duplicate legacy code (safe to delete), and (b) a real, finished, tested feature that simply hasn't been wired to a route yet (should be completed, not destroyed).

**How to tell them apart before deleting:** read the file's own test suite and `git log --oneline -- <file>` before acting on a DEAD classification whose triage note flags money, PII, or an explicit design decision (self-referral guards, idempotency keys, atomic RPCs). Signals it's case (b), not (a):
- A `__tests__` file exists and is comprehensive (not a stub), with test names referencing a specific task ID (e.g. `// MNY-3: self-referral guard`).
- `git log` shows the surrounding function was *extended* recently (not just originally authored long ago) — a fresh commit adding a guard/atomicity fix to code that's otherwise old is a strong tell someone is actively investing in it, not abandoning it.
- The code already does the "right" thing for a missing table (propagates real errors, narrows `PGRST116` correctly) rather than silently swallowing — sloppy, truly-dead code usually doesn't bother getting error handling right.

**Why:** Found 2026-07-31 on `user_attributions` (gamification/growth cluster, commit `df3e1f0`). Triage correctly flagged it DEAD (`affiliateService.applyReferralCode()` has zero live callers) and recommended deletion. But `affiliate-service.test.ts` had full, passing coverage for `createAttribution`/`getUserAttribution`/`updateLastClick`/`getReferrer`, and `git log` showed `applyReferralCode` was extended with an atomic `increment_referral_use()` RPC and a self-referral guard via a recent, explicitly-labeled commit (`37c7531`, "TASK-MNY-02/03"). Deleting those methods to satisfy the DEAD/"Delete" recommendation would have thrown away tested, money-adjacent (referral attribution → commission) work for zero benefit — the actual fix was a 90-line additive migration, not a deletion, and required zero application-code changes since the existing error handling was already correct.

**How to apply:** When a DEAD-classified table's owning code has passing tests and recent git activity, treat "build the missing table" as the default hypothesis, not "delete the code" — even though building is *more* work than deleting. This is a "no quick fixes" case: the additive migration is the durable, correct answer; deleting tested code because a mechanical reachability check didn't find today's caller is the shortcut. Still delete freely when the file has zero tests, zero recent commits beyond original authorship, or (the common case in this cluster) is a duplicate of a live, already-backed system — e.g. the sibling `user_achievements`/`achievement_definitions` finding in the same triage, a 1,554-line duplicate of the already-shipped `badge_definitions`/`user_badges` system, was correctly deleted, not rebuilt.

**Confirmed a second time, 2026-07-31, credit/identity cluster (commit `bca74a1` correcting `5635b21`):** deleted `CreditBuilderLoanService.ts` + `RentReportingService.ts` (both DEAD by reachability — no live route imports either) without checking `git log --follow` first. Both had comprehensive `.test.ts` files *and* a dedicated `.idor.test.ts` each, added by a recent, explicitly-labeled commit (`2a99c6d`, "TASK-CRD-2 IDOR sweep") that hardened `updateApplication`/`updateAccount`/`getPaymentHistory` against cross-user access — the exact signal this memory names. Caught only because I read this file before calling the deletion "done." **Run `git log --oneline --follow -- <file>` on every DEAD candidate before deleting it — not just when something feels off** — two original-authorship-only commits (safe to delete) look identical to a mechanically-reachability-DEAD file at a glance; only the log distinguishes them.

**Restoration technique, if you catch this after already deleting+committing:** `git checkout <commit-before-the-deletion> -- <paths>` restores the exact pre-deletion content into the working tree *and* stages it in one step (find the parent via `git log --oneline -- <path>`, the second-most-recent entry). Cleaner than `git revert` for a partial file set, since revert would also undo whatever else was correct in that same commit. Commit the restoration as a new, clearly-labeled correction commit — don't amend or force-push over the wrong one.
