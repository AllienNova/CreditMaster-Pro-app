While wiring `/api/privacy/export|delete|consent` (team-lead brief: "the service layer exists and works, there is no route to it"), reading `gdpr-ccpa.ts` in full surfaced that the service layer did NOT fully work: `GDPRComplianceService.exportUserData`'s five private helpers (`getUserProfile`, `getUserCreditReports`, `getUserDisputes`, `getUserAIInteractions`, `getUserLogs`) and `ConsentManagementService.getUserConsents` all swallowed a genuine DB error into `null`/`[]` — indistinguishable from "user genuinely has no data." A transient permission or connection failure on any one export query would have silently omitted that category while the route still returned `success: true`. `exportUserData` had **zero** prior test coverage anywhere in the repo (confirmed by grep before writing tests) — this had never been exercised.

**Fixed** (commit `2aef1d8`, same commit as the route wiring — judged in-scope because it's required by the brief's own explicit "honest failure" mandate, and it's the exact code path the new routes serve data from): each list-query helper now throws on a non-null `error` (list queries have no legitimate "not found" error code — an empty result is `{data: [], error: null}`, so any non-null error is real). `getUserProfile` (a `.single()` query) keeps `PGRST116` → `null` (genuine not-found) but throws on any other error code, matching the established repo idiom (see [[jest-resetmocks-and-postgrest-errors]] item 3). Added `src/lib/compliance/__tests__/gdpr-export.test.ts` (new file, 9 tests) and extended `gdpr-ccpa-consent.test.ts` with 2 tests for `getUserConsents`. Red-before-green proven via a scoped stash of just `gdpr-ccpa.ts` (see [[scoped-stash-shared-worktree]]) — 6 failures pre-fix, 0 post-fix, 179 pre-existing compliance tests unaffected.

**Why this matters beyond the immediate fix:** this is the same defect class as the `audit_logs`/erasure-RPC and `tax_profiles` findings in this memory store — a service silently reports success/empty on a real failure. It's worth checking for the same pattern (`if (error) return null/[]` without distinguishing a genuine not-found code from an unrelated failure) in any other `gdpr-ccpa.ts` method or sibling compliance service before trusting its output as ground truth.

**How to apply:** `exportUserData` and `getUserConsents` can now be trusted to throw rather than misreport on a real DB failure. If extending `gdpr-ccpa.ts` further (e.g. wiring `rectifyUserData`/`restrictProcessing`/`objectToProcessing` to routes — these were NOT touched, out of scope for the privacy-routes task), re-check their error handling with the same lens before assuming they're honest; they already throw on error today per the code as read 2026-07-31, but weren't specifically re-verified with new tests as part of this pass.
