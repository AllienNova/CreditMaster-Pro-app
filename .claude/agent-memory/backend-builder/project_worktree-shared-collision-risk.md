In `.worktrees/wave-7-foundation` (branch `remediation/wave-7-foundation`), on 2026-07-24 two files I had just edited and verified (`src/app/api/admin/subscriptions/route.ts`, `src/app/api/admin/disputes/route.ts` — plus their test files) were silently reset back to their pre-fix content partway through a multi-item task. `git status --short` showed zero diff against HEAD for those exact paths (i.e. they matched a commit that predated my fix), while three OTHER files I'd fixed in the same session survived intact because something had already auto-committed them (`git log` showed real commits I never made, e.g. `5e48020`, `21d01e6`, with messages accurately describing my own changes). No destructive command was run by me — `git status --short` on the untouched files also came back clean pre- and post-collision, and nothing else in the worktree looked touched.

**Why:** this is a shared worktree with many concurrently active teammates (team-lead runs `fix-docs`, `fix-erasure-resilient`, `fix-lint`, `fix-mny-rail`, `fix-mobile-types`, `fix-payout-fees`, `parity-audit`, `vcrit-*` critics, etc. per the session's teammate list). Something — most likely an automated per-agent-turn commit/checkpoint process — appears to periodically snapshot the working tree, and on at least one occasion that snapshot/reset window landed between when I finished an edit and when I got around to committing evidence, wiping the uncommitted portion.

**How to apply:** After any edit in this worktree (or a similarly multi-agent shared worktree), verify with `grep`/`git status --short <path>` on the SPECIFIC files just touched before assuming a "wasted call — file unchanged" Read result means your edit is intact — that message only means the file matches your last tool-call view of it, which is exactly what a revert-to-a-prior-state would also look like from the harness's perspective once your Edit result is stale. If a file you just fixed shows zero `git diff` against HEAD when you expect a real change, that's a red flag it was reset, not a sign the fix "wasn't needed." Move fast (batch the fix + test + verify with minimal delay) on any task in this worktree, and re-verify ground truth via grep immediately before reporting done. Flag any recurrence to team-lead — don't just silently redo it forever. See [[msw-fetch-mock-pattern]] for the unrelated test-infra gotcha hit in the same session.

**Resolution (2026-07-24):** team-lead independently hit a stale snapshot of the same collision — believed item 4 was reverted/broken and said so, when my redone+reverified fix was actually sitting correct and green on disk. I pushed back with fresh `git status`/grep evidence instead of standing down on the stale premise; team-lead then read the actual files, re-ran the 22 tests, confirmed green, and committed+pushed (`9086c75`) — nothing was lost. Confirmed team-lead's mitigation going forward: verify a subagent's edits directly on-disk (fresh tsc/grep) before trusting a snapshot, rather than relying on whatever state was captured mid-edit. Takeaway holds in both directions — don't trust a stale "it's broken" report about your own work either; re-verify current disk state before accepting either a revert OR a "looks fine" claim.
