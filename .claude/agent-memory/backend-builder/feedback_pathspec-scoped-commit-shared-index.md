description: How to commit safely in a shared worktree when the git index already contains another agent's staged changes, OR when another agent has co-edited the exact same file you're committing
metadata:
  type: feedback

In a shared worktree, the git index is shared too — not just the working tree. If another agent has already run `git add` on their own files (e.g. mid-flight deletions) and you then `git add` your own files and run a plain `git commit`, the resulting commit silently includes their staged changes as well, attributed to your commit message. `git status`/`git diff --cached --stat` will show far more files than you touched — that is the tell.

The fix: `git commit -m "..." -- <your-exact-paths>` (pathspec after `--`, no `-a`, no `-i`). Confirmed via official git-scm.com docs (`git commit` reference, the `<pathspec>` argument description and its worked `hello.c`/`hello.h`/`Makefile` example): when pathspec is given without `-a`/`--interactive`/`--patch`, the commit **only** records the current content of the named paths and leaves every other already-staged path untouched in the index for a later commit. You don't need to unstage anything first — just point the commit at exactly the paths you own.

**Why:** Found 2026-07-31 while landing two independent fixes (`demotion-rules.ts`, `payout-service.ts`) in `.worktrees/wave-7-foundation`. `git diff --cached --stat` before committing showed 22 files — my 4 plus ~18 files another agent (`deadcode-duplicates`) had already staged for deletion (achievements, mfa-service, affiliate, offers, matching, email-preferences). A plain `git commit` would have folded their in-progress deletions into my unrelated fix commit.

**How to apply:** Before every commit in a shared worktree, run `git diff --cached --stat` (or `git status --short`) first. If it shows anything beyond the paths you just edited, do not run a bare `git commit` — use `git commit -m "..." -- <your paths>` instead. Verify after with `git diff --cached --stat` / `git log --oneline -1 --stat` that the landed commit touched only your files, and that the other paths are still sitting staged (untouched) for their owner to commit separately. Complements [[scoped-stash-shared-worktree]] (that one is for proving red-before-green without disturbing others; this one is for the commit step itself).

**Confirmed robust even when another agent commits mid-flight (2026-07-31, `financial-chat-engine.ts` fix, commit `058a501`):** between my `git pull --ff-only` and my `git commit -- <my 2 files>`, a different concurrent agent committed their own scoped fix (`fed16a9`, touching `financial-aggregation-service.ts`/`savings-optimizer.ts`) directly to the same local branch — this is possible because a shared worktree is the same literal `.git` directory across agent processes, not just a shared working tree. `git diff --cached --stat` looked empty right after my commit, which read at first glance like their staged changes had been swept in — they hadn't; their commit had simply landed in history in between (confirmed via `git log --oneline -3` and `git show --stat HEAD` showing my commit contained only my 2 files). Don't skip the post-commit `git show --stat HEAD` sanity check just because `git diff --cached --stat` looks clean — check `git log` too before concluding something went wrong.

**CORRECTION — the "safe even under this race" claim above is FILE-level pathspec safety only, NOT hunk-level, and does not extend to files two agents co-edit (2026-07-31, same session, `fix-debts-rename` agent).** Per the local `git commit --help`, `<pathspec>` section, verified word-for-word: "commit the contents of the files that match the pathspec **without recording the changes already added to the index**. The contents of these files are **also staged** for the next commit on top of what have been staged before." That commits the pathspec'd file's **current working-tree content, in full** — not "only the diff you personally authored" and not "only what you staged." It protects you from sweeping in *other, differently-named* files another agent has touched (that's what the paragraph above demonstrates). It does **not** protect you when another agent has modified the *same* file you're committing: `financial-aggregation-service.ts` had my `fetchDebtData` fix AND a concurrent agent's uncommitted `fetchCreditData` fix in the same working tree; `git commit -m "..." -- src/lib/financial/financial-aggregation-service.ts <3 other files I owned>` committed **all 5 hunks** (my 2 plus their 3) under my commit message — confirmed via `git show <sha> -- <file> | grep '^@@'` listing all 5 hunks. `git diff --cached --stat` before committing would have caught this (it still shows everything about to be swept in for a co-edited path); the mistake was checking hunk boundaries once via `git diff -U1 -- <file> | grep '^@@'` and then trusting file-level pathspec scoping to preserve that split through the commit — it doesn't.

**How to apply, when the same file has co-edits (not just co-touches):** file-level pathspec scoping is not enough. Extract only your hunks into a standalone patch (`git diff --no-color -- <file> > /tmp/full.diff`, identify your hunk(s) via `grep -n '^@@'` plus reading each hunk's content, `sed -n '<header-line>,<next-header-line-minus-1>p'` the file's `diff --git`/`index`/`---`/`+++` header lines plus just your hunk(s) into a new patch file), then `git apply --check --cached <patch>` to dry-run, then `git apply --cached <patch>` to stage precisely those hunks — leaves the other agent's hunks unstaged in the working tree, untouched, for them to commit separately. This is what actually worked; the commit itself must then still be `git commit -m "..." -- <the same file + your other owned files>` (pathspec is still required to avoid sweeping in *unrelated* staged files per the paragraph above) — **but only after you've confirmed via `git diff --cached --stat` / `git show --stat` that the index for the co-edited file already matches your hunks only.** If a concurrent agent pushes before you can split and push your own commit (as happened here — their push carried my already-created, over-inclusive commit along as an ancestor), the mistake is now published: do **not** force-push/rewrite to fix it (hard limit, needs explicit sign-off) — verify the bundled content is actually correct (it was, in this case: both fixes were independently tested and correct, just mis-attributed), message the affected agent so they know their work already landed under someone else's SHA, and report the mis-attribution honestly rather than hiding it.

**Two mechanical gotchas with the `git commit -m "..." -- <pathspec>` form itself (2026-07-31, gamification-cluster cleanup, commit `df3e1f0`):**
1. **`-m` must come *before* `--`, not after.** `git commit -- <paths...> -m "msg"` fails: everything after `--` is parsed as pathspec, so `-m` and the entire message string get treated as (non-matching) path arguments and the commit errors out on all of them, including your real files. Always: `git commit -m "$(cat <<'EOF' ... EOF)" -- <paths...>`.
2. **A brand-new untracked file is NOT auto-included by pathspec alone.** Unlike a modified-but-unstaged tracked file (which pathspec *does* pick up from the working tree per the git-scm docs quoted above), a file `git` has never seen before must be `git add`ed first — `git commit -m "..." -- path/to/new-file.sql` on its own errors with "pathspec ... did not match any file(s) known to git" even though the file exists on disk. Fix: `git add <new-file>` first, then run the pathspec-scoped commit as usual (the new file will now show `A` in `git status` and the commit works normally). Tracked-modified and staged-deleted paths in the same commit don't need this extra step — only genuinely new files do.

**`git commit --amend` (no pathspec) is categorically worse than a bare `git commit` — it commits the ENTIRE current index, discarding the pathspec-scoping the original commit had (2026-07-31, savings/goals cluster, commit history `e1b1f4b` → wrongly amended to `e0a38fa` → recovered to `6766a3a`).** After landing a clean pathspec-scoped commit (`git commit -m "..." -- <my 16 files>`, correctly 518+/7784-), I found one stray backtick in the commit body and ran `git commit --amend -m "<fixed message>"` with **no trailing `-- <pathspec>`** to fix just the wording. Result: the amend silently expanded from 16 files to 29 — it pulled in everything OTHER agents had staged in the shared index in the meantime (a credit-builder service, a rent-reporting service, deletions of `alternative-asset-service.ts`/`AutoRebalanceScheduler.ts`/`PortfolioRebalanceService.ts`/`proactive-alert-engine.ts` that belonged to `deadcode-*` agents), all now falsely attributed to my commit message. `--amend` doesn't remember "only touch the paths the original commit touched" — it rebuilds the commit from whatever is in the index *right now*, exactly like a bare `git commit` with zero pathspec.

**How to apply:** never bare-amend in a shared worktree, for *any* reason (message typo, forgotten file, whatever) — always `git commit --amend -m "..." -- <the exact same pathspec as the original commit>`. If you only need to reword the message and are certain nothing else has been staged in the meantime, still pass the pathspec defensively; it costs nothing and the failure mode when you're wrong is silent and severe (false attribution of other agents' possibly-incomplete work).

**Recovery, if you already ran a bare `--amend` and haven't pushed:** `git reset --mixed <sha-of-the-good-commit>` restores the branch to the correct commit and unstages the swept-in files back to the working tree (their actual file *content* on disk is never touched by any of this — only the index/HEAD — so nothing is lost, the other agents just need to re-`git add` when ready). Get `<sha-of-the-good-commit>` from the amend command's own terminal output (it prints the old SHA) or `git reflog`.

**Even that recovery can re-race — the shared index keeps moving underneath you.** After the reset, re-diffing a contested file (`git diff -- src/lib/financial/index.ts`) against my restored "good" commit *still* showed another agent's unrelated hunk baked in — meaning my very first commit had already raced (a concurrent `git add` on that same path landed between my `git update-index --cacheinfo <my-blob>` and the `git commit` that followed, silently overwriting the manually-crafted blob before the commit read the index). Pathspec at commit time only protects against *other files*; for a path under **active** concurrent edit, the window between staging and committing is still a race, no matter how it's staged. **The robust fix is to bypass the mutable index entirely for the contested path:** stage everything else normally, `git write-tree` to snapshot, independently verify that tree object with `git diff <parent> <tree-sha> -- <contested-file>` (diffing two immutable objects, not the live index — this can't be raced), then `git commit-tree <verified-tree-sha> -p <parent> -m "..."` to build the commit directly, `git update-ref refs/heads/<branch> <new-commit-sha>` to move the branch, and finally `git reset --mixed HEAD` to resync the index without touching anyone's working-tree files. Slower, but the verification step makes it provably correct instead of "probably fine."

**A `git rm`-staged deletion can silently fall back OUT of the index before you commit, with no error at any step (2026-07-31, trading/assets cluster, commit `9b5ac20` → corrected in `99a579c`).** `git rm PortfolioRebalanceService.ts AutoRebalanceScheduler.ts alternative-asset-service.ts alternative-asset-service.test.ts` succeeded and staged all 4 (confirmed by its own `rm '...'` output lines). Sometime later — after two *other*, unrelated `git add` batches of mine each failed atomically on an already-gone pathspec (exit 128, per the "atomic across the whole pathspec list" behavior already documented for `git rm`/`git add` elsewhere in this file) — a final `git diff --cached --stat` right before commit genuinely did not list those 4 files at all, and I misread the output as complete instead of noticing the absence. The bare `git commit -m "..."` (no pathspec — a mistake on its own, but not the root cause here) then committed only what the index actually held at that instant, which no longer included those 4 deletions. Post-push, `git cat-file -e HEAD:<path>` showed all 4 files **still present in the committed tree** while genuinely absent from the working tree (`git status` showed them as fresh, unstaged `D` entries) — i.e. the index entries for those 4 paths had reverted to matching HEAD sometime between my `git rm` and my `git commit`, almost certainly from another concurrent agent's unrelated index operation on this same shared `.git` directory (this exact file's own file list — `alternative-asset-service.ts`/`AutoRebalanceScheduler.ts`/`PortfolioRebalanceService.ts` — is independently referenced two paragraphs up as swept into a *different* agent's bare `--amend` the same session, confirming multiple agents were mutating the index for these exact paths concurrently).

**How to apply:** `git diff --cached --stat` immediately before a commit is a snapshot of the index *at that moment* — it is not a guarantee about what will actually land, because the index can still be mutated by another agent's process between that check and the `git commit` call (there is no atomicity across separate commands, only within one). Treat a pre-commit diff review as necessary but **not sufficient**. After every push in a shared worktree, run a post-hoc check on the *actually-committed, pushed* tree for anything security- or completeness-sensitive — `git cat-file -e HEAD:<path>` (exits non-zero if absent) for files you deleted, or `git show HEAD:<path> | grep -c <symbol>` for files you edited — rather than trusting the pre-commit review alone. If a gap is found post-push, don't rewrite history to fix it (hard limit) — stage exactly the missing paths and land a small, honestly-labeled follow-up commit, same as any other correction.
