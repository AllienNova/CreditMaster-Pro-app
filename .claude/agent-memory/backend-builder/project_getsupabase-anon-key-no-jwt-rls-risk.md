`getSupabase()` in `src/lib/supabase/client.ts` calls `createSupabaseClient(NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY)` with no session, no cookie forwarding, and no `Authorization` header override. It is a bare anon-key client. Every server-side service that does `const supabase = getSupabase();` at module scope (confirmed: `credit-bureau-service.ts`, `credit-monitoring-service.ts`, and by pattern likely most of `src/lib/**`) therefore talks to Postgres as the unauthenticated `anon` role — `auth.uid()` resolves to `NULL` inside any RLS policy evaluated on those connections, regardless of which end user actually triggered the request.

This matters because the established RLS idiom across this schema (`disputes`, `credit_accounts`, `bureau_connections`, the `bureau_disputes`/`credit_alerts` tables added in commit `2bc57fd`, and many more) is `USING (auth.uid() = user_id)` / `WITH CHECK (auth.uid() = user_id)`. If `auth.uid()` is genuinely always NULL on these connections, every one of those policies silently blocks the exact writes the application code performs — `NULL = user_id` is `NULL`, not `TRUE`. A working production app strongly implies this is NOT actually happening (either something forwards the JWT that this file's Proxy pattern doesn't make obvious, or these specific tables/policies are more decorative than load-bearing at runtime and something else is doing the real access control) — but I could not find the mechanism in the time this task allowed, and did not chase it further since it is a cross-cutting, pre-existing concern spanning dozens of files, not specific to the two bugs I was assigned.

Contrast: `src/lib/supabase/server.ts` and `src/lib/supabase/admin.ts` both exist and use `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS entirely). Some tables in this schema (`bill_alerts`, `emotional_spending_alerts`) have NO insert RLS policy at all — meaning their writes were clearly designed to go through a service-role connection, not the anon-key `getSupabase()`. That split (some services assume anon-key + forwarded JWT, others assume service-role bypass, with no obvious rule for which is which) is itself worth someone auditing.

**Why:** Discovered while designing RLS for `bureau_disputes`/`credit_alerts` (docs/qa/SYSTEMATIC-REVIEW-SYNTHESIS.md findings #6/#7) — needed to decide whether an INSERT policy was load-bearing or decorative for tables written exclusively through `credit-bureau-service.ts`/`credit-monitoring-service.ts`'s `getSupabase()` calls, and could not confirm from the code whether `auth.uid()` is ever non-NULL on that client.

**How to apply:** Do not assume an `auth.uid() = user_id` RLS policy is actually the enforcement mechanism for a table written through `getSupabase()` (`@/lib/supabase/client`) without verifying JWT forwarding first — grep for where the connection's `Authorization` header or session gets set, or run a real integration test against local Supabase with `NODE_ENV` matching production request handling. If asked to harden auth/authz on a route whose service uses `getSupabase()`, this is the first thing to check, not the RLS policy text.
