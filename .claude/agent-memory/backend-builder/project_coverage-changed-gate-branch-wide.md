`npm run test:coverage:changed` (`scripts/check-changed-coverage.js`) resolves its base ref to `origin/main` (falling back through `main`/`origin/master`/`master`) and diffs the entire working tree against that base — which on a long-lived branch like `remediation/wave-7-foundation` means the WHOLE branch's cumulative diff since it forked from main, not just the current session's uncommitted edits. As of 2026-07-31 this reported 636 files "under gate" and 220 failing, almost none of which belonged to the task at hand (a 3-file fix).

Don't read the aggregate "N file(s) below 85%" failure count as a signal about your own change. Instead grep the full log (redirect both stdout+stderr correctly: `> file 2>&1`, not `2>&1 > file` — the latter splits them across destinations and will hide the per-file PASS/FAIL lines) for your exact changed file paths; each gated file gets exactly one line, either `PASS  100.0% of N changed point(s)  <file>`, `PASS  no executable code on changed lines  <file>` (comment-only diffs), or a failure line. Confirmed this session: a 3-file diff (2 route files + 1 comment-only type file) showed 100%/100%/no-executable-code individually, while the aggregate summary showed 220 unrelated failures from other agents' concurrent work and prior branch history.

**Why:** Nearly mistook 220 pre-existing, out-of-scope failures for a blocker on a narrowly-scoped fix; would have wasted significant time investigating or (worse) been tempted to "fix" files outside the assigned task.

**How to apply:** Whenever running this gate on this branch, grep the log for your own paths specifically rather than trusting the pass/fail exit code or the aggregate count alone.

**When your own file genuinely fails (2026-07-31, budget-service.ts, commit `89718c2`):** the gate only prints an aggregate `X.X% of N changed point(s)`, never which lines. `scripts/check-changed-coverage.js`'s own `changedLinesByFile()` + `diffCoverage()` functions are trivial to re-run standalone in a `node -e` one-liner: (1) `git diff --unified=0 --diff-filter=ACMR origin/main -- <file>` and parse `@@ -a +b,c @@` hunks into a `Set` of changed line numbers (only the `+b,c` side matters), (2) regenerate `coverage/coverage-final.json` via `npx jest <test files> --coverage --collectCoverageFrom=<file> --coverageReporters=json --silent`, (3) walk `entry.statementMap`/`entry.branchMap`, keep only entries whose `start.line` is in the changed-lines set, and check `entry.s[id]`/`entry.b[id][k] > 0`. This reproduces the script's exact 84.0%/100.0% number and additionally names the specific uncovered `{line, type}` points (e.g. a `binary-expr` branch is an untested `||` fallback side, a bare statement is a whole line never executed) — turns "add tests covering the changed lines above" into an exact, bounded todo list instead of re-reading the whole diff hoping to spot the gap.

**Sibling gotcha — plain `npx jest` / `npx tsc --noEmit` (no coverage-changed script involved) are ALSO a moving target on this branch, for a different reason (2026-07-31, gamification-cluster verification).** With 4-5 agents editing concurrently, three consecutive full-suite `npx jest --no-coverage` runs during one verification pass showed **different** total test-suite counts (804 → 802 → 794) and **different** failing suites each time (payments-ledger TypeError+admin-metrics-$0 → a wall-clock-dependent notification flake → unrelated credit-monitoring errors) — none touching the files under test. Same root cause as the coverage-changed aggregate, different command: a repo-wide command run against a live, simultaneously-mutating working tree captures whichever partial mid-edit state every other agent happens to be in at that instant, not a stable signal about your own change. `npx tsc --noEmit` hit this too — clean (0 errors) immediately after my edit, then showed unrelated `never`-type overload errors in a file I'd never touched a few minutes later (another agent's concurrent, uncommitted schema-rename in progress). **How to apply:** trust a directory/file-scoped `npx jest <your paths>` re-run 2-3× (stable, deterministic, isolated from other agents' files) over a repo-wide run; if a repo-wide run shows unrelated failures, check `git status` for who else has that path modified/staged before assuming it's yours to fix — and don't chase a "clean full suite" snapshot that may not be achievable except by coincidence while others are mid-edit.
