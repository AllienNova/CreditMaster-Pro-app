name: scoped-stash-shared-worktree
description: How to prove red-before-green safely when other agents have concurrent uncommitted work in the same worktree
metadata:
  type: feedback
---

To verify red-before-green against pre-fix code in a shared worktree (multiple agents editing different files concurrently, e.g. `.worktrees/wave-7-foundation`), never run a bare `git stash` — it stashes every other agent's uncommitted work too. Instead use a path-scoped stash: `git stash push -m "<label>" -- <exact file path>`, which reverts only that one file to HEAD. Run the new test (expect failure), then `git stash pop` to restore the fix, then re-run (expect pass). Confirmed working: `git diff -- <path>` is empty immediately after the scoped push, and `git stash pop` cleanly restores exactly that file with no side effects on other dirty files in the tree.

**Why:** Discovered while fixing the `tax_accounts` phantom-table bug (commit 59c82bb) — the team-lead's brief explicitly flagged another agent (`build-trading-persistence`) was actively editing `src/lib/trading/**` in the same worktree at the same time. A full `git stash` would have swept up that agent's in-progress work.

**How to apply:** Any time a task in a shared/team worktree needs genuine red-before-green proof (not just code-reading confidence) and the fix touches only a small number of files. Doesn't scale to fixes spanning many files with interdependencies (would need multiple scoped stashes in the right order) — for those, prefer reasoning from a direct source read plus a fresh isolated checkout if literal execution is required.

**Refinement (2026-07-31, budget-service.ts fix, commit `89718c2`):** When the fix spans a source file *and* a hand-declared type file it depends on (e.g. `budget-service.ts` + `budget.types.ts`'s `BudgetRow`), stash **both together** in one `git stash push -- <path1> <path2>` — not just the logic file. If `ts-jest` type-checks (no `isolatedModules` in `tsconfig.jest.json`), reverting only the logic file while the type file already has the fix applied can produce a compile error instead of a clean runtime red, which proves nothing useful. Also: if the natural order is "write the new/failing tests before touching source at all" (true TDD, not retrofitting tests onto an already-fixed implementation), you get an equally valid — arguably cleaner — red-before-green with **no stash needed at all**: write tests, run (red, against genuinely untouched source), implement the fix, run again (green). Only reach for the stash when a test is added *after* the source fix already exists (e.g. a coverage-gap test written once diff-coverage flagged a miss).

**Refinement — a scoped stash can outlive its safety window if the owning agent edits the same files while it's active (2026-07-31, gamification-cluster verification, commit `df3e1f0`).** Stashed 3 files belonging to a concurrent agent's in-flight task (to prove my own full-suite run clean of their 2 known-WIP failures), then tried `git stash pop` ~20s later — it **aborted** with "Your local changes ... would be overwritten by merge" because that agent had pushed further edits to those exact 2 files on disk *while the stash was active*. This is git behaving correctly (transactional: nothing was applied, "the stash entry is kept in case you need it again," and my own unrelated staged files were completely unaffected by the failed pop). Do not force it. Instead: `git diff stash@{N} -- <each conflicting file>` to compare the stashed snapshot against the new on-disk state. If the on-disk version is a strict superset/improvement (confirmed here: they'd fixed the exact bug — a `/100` double-division cents/dollars error — that was causing the failures I was isolating around), the stash is now stale and redundant; either `git stash drop` it or, if it's not unambiguously your own work to discard (it was seeded from *their* files), leave it and flag it in your handoff report rather than unilaterally dropping someone else's related-content stash.

**CORRECTION — a *correctly path-scoped* stash still disrupted another agent's live work; scoping prevents collateral damage to unrelated files, not disruption to the target files themselves (same 2026-07-31 episode, team-lead follow-up).** The team lead reported the stash "silently destroyed my in-progress edits and I had to redo them" — this was NOT a bare-stash mistake (verified against my own tool-call record: the command was `git stash push -- <exact 3 paths>`, and `git status` after the failed pop confirmed all 15 of my unrelated staged deletions were completely untouched throughout). What actually happened: `git stash push -- <path>` *does* revert the named paths to HEAD in the working tree for as long as the stash is active — even scoped to exactly the right files, this is still disruptive if the file's owning agent is actively reading/editing/saving that exact file at that moment, because their uncommitted changes momentarily vanish from disk. The team lead's `git stash show --stat stash@{0}` (misread as "no pathspec" because `--stat`/`show` reports the full tree-relative diff, including files that were merely *already staged* at push-time, not just the pathspec-reverted ones — same quirk noted below) escalated a real-but-different problem into a wrong diagnosis; both things were still worth surfacing.

**Sharper how-to-apply:** treat "which other agent's files, if any, do I need to stash" as a question to answer via `git status`/`git log -1 --format=%cr -- <path>` (how recently touched) *before* stashing, not just *whether* to pathspec it. If a file was modified in the last few minutes, assume the owning agent may be actively mid-edit and prefer a non-destructive isolation method instead: (a) diff-based attribution (`git status` + `git diff` to identify whose files are involved, then reason about causation without touching them at all — this is what actually resolved the ambiguity here, the stash wasn't even necessary in hindsight), or (b) ask the owning agent directly via a message before touching their files, or (c) if isolation is genuinely required, `cp` the target file(s) to `/tmp` first as your own safety net independent of stash mechanics. After any stash-based isolation (successful or aborted), verify your own files landed safely elsewhere (committed, or still correctly staged) — if 100% of what's yours is already committed/pushed and 100% of what's someone else's is confirmed stale/superseded by their own newer commit, `git stash drop` it rather than leaving a confusing, already-redundant snapshot sitting in the shared stash list for someone to misread later, as happened here.
