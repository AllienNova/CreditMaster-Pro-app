# Phantom-Table Triage — Identity / Auth / Credit / Notifications / Documents / Platform

Slice owner: `triage-platform`. Scope: 30 assigned phantom tables.
Schema verified against the live DB (56 migrations applied, 146 public tables) via
`PGPASSWORD=postgres psql -h 127.0.0.1 -p 54322 -U postgres -d postgres`.
Call sites collected with `grep -rn '\.from("<table>")' src mobile-app/src mobile-app/app`, excluding `__tests__` and `*.test.*`.

## Method notes

- **Every one of the 30 tables is absent from the live schema.** Independently, `grep -rl 'CREATE TABLE[^;]*<table>' supabase/migrations` returns **NONE** for all 30 — no migration creates any of them, applied or shadowed. There is no "unapplied migration" explanation to fall back on.
- **Classification precedence.** Where calling code is provably unreachable, the row is classified `DEAD` even when a rename target exists, because the recommended action is deletion rather than migration. The rename target is still recorded in the *real equivalent* column so the information is not lost.
- **Reachability proof standard.** `DEAD` is asserted only where a content grep for every exported symbol of the owning module across `src` + `mobile-app` returns nothing outside the module's own file, its barrel, and its tests. Where I could not prove deadness, the row is treated as live.
- **Mobile is clean.** The full set of non-test `.from("...")` targets under `mobile-app/src` + `mobile-app/app` is exactly `disputes` and `profiles` — both real tables. **Zero** of these 30 phantoms are reachable from the mobile app.

## Top 5 by real security / compliance / user impact

**1. `bureau_disputes` — dispute filed with the bureau, recorded nowhere, reported as failed.**
The only finding here where the system takes an irreversible action against a third party and then loses the record. `submitDispute` gates persistence on `if (response.success)` (`credit-bureau-service.ts:736`), so the bureau has already accepted the dispute and the FCRA §611 30-day reinvestigation clock is running. `saveDisputeRecord` then throws on the phantom table (`:1204`), the enclosing `catch` at `:748` swallows it, and the caller receives `{ success: false }`. Three consequences compound: the consumer is told their dispute failed; no row exists to track the bureau's response deadline; and a retry files a duplicate dispute, which bureaus may treat as frivolous under §611(a)(3). This is the one item on the list that creates an external, unrecoverable state divergence.

**2. `credit_builder_actions` + `user_profiles` — fabricated credit-improvement progress served to consumers.**
`GET /api/credit-builder/progress` is an authenticated route returning invented numbers to every user: `actionsCompleted` defaults to `8` and `actionsTotal` to `12` (`credit-builder-service.ts:538-539`), target score to `720` (`:527`), and account tenure to a hardcoded 90 days (`:532`). A user who has completed nothing sees "8 of 12 actions completed" on a credit product. This is worse than an empty-data computation — it is affirmative misrepresentation of a consumer's progress on an FCRA-adjacent service. **It also does not self-heal:** because the code uses `||` rather than `??`, a legitimately empty result (`[].length === 0`) is falsy and still yields `8`. Creating the table fixes the phantom but leaves the fabrication intact; both must be fixed.

**3. `credit_alerts` — credit monitoring that cannot raise an alert.**
`createAlert` returns `null` on failure (`credit-monitoring-service.ts:431`) and `getAlerts` returns `[]` (`:360`), so `GET /api/credit-monitoring/alerts` returns an empty list indistinguishable from a genuine all-clear. Credit alerts are the detection mechanism for new-account fraud, unauthorized inquiries, and score collapse — the specific consumer-protection function a monitoring product is sold to perform. Every alert this system has ever tried to raise was discarded silently. Placed above `credit_profiles` because the failure is undetectable by the user: a zeroed score is visibly wrong, an empty alert list looks like good news.

**4. `credit_profiles` — every financial health score computed from a credit score of 0.**
Three live routes (`/api/financial/aggregated`, `/api/financial/health-score`, `/api/financial/health-score/v2`) call `fetchCreditData`, which falls back to `getEmptyCreditProfile()` returning `currentScore: 0` (`financial-aggregation-service.ts:757,1413`); that value flows into scoring at `:245`. The sharp detail is that **the real data already exists** — `credit_scores` and `latest_credit_scores` are populated real tables — so this is a pure wiring defect, the cheapest CRITICAL on the list to close and the one with the widest user-visible blast radius.

**5. GDPR/CCPA data-subject rights are not reachable at all — `ai_interactions` is only the symptom.**
Classified LOW as a table because the code is provably dead, but the reason it is dead is the actual finding, and it is CRITICAL. `GDPRComplianceService.exportUserData` (Art. 15/20) and `deleteUserData` (Art. 17) have no caller outside `gdpr-ccpa.ts`. `CCPAComplianceService` and `ConsentManagementService` have **zero** consumers in `src/app` or `mobile-app`. The sole route importing the module uses only `notifyDataBreach`. There is no `/api/privacy/*`, `/api/gdpr/*`, or user-facing export or erasure endpoint anywhere in `src/app/api`. **A user cannot exercise any data-subject right through this product.** Consistent with the already-proven Art. 17 erasure abort — the erasure code is both broken and unrouted. When the route is built, `getUserAIInteractions` must be repointed at the real `chat_messages` / `financial_chat_messages` / `ai_coaching_sessions` tables; an export that silently omits AI conversation history would be an incomplete Art. 15 response.

## Findings beyond the table scope

Surfaced during triage, outside the phantom-table remit, recorded so they are not lost:

- **`src/lib/auth/mfa-service.ts` is a dead parallel MFA implementation** shadowing the working `src/lib/auth/backup-codes.ts`. Recommend deletion rather than repair — leaving it invites a future wiring-up that fails closed on every backup code (account lockout).
- **The nudge delivery layer is unimplemented.** `sendPushNotification`, `sendEmailNotification`, and `sendSmsNotification` (`nudge-engine.ts:237,264,290`) contain no provider call — only `// Would send to device(s)` / `// Email queued` / `// SMS queued` comments. Fixing `users` and `user_devices` delivers nothing on its own.
- **Two IDOR regression suites guard unreachable services** (`shared-goals-service.idor.test.ts`, `financial-journey-service.idor.test.ts`, `CreditBuilderLoanService.idor.test.ts`). They contribute coverage and confidence for code no route can reach.
- **Nothing in production writes a tax-document access log.** `tax_document_access_log` is test-only; whether reads of `tax_documents` are audited via `tax_audit_log` was not verified and sits outside this slice.
- **Verified clean:** the CAN-SPAM unsubscribe path works. `/api/email/unsubscribe` persists to the real `user_settings` and writes `audit_logs` (`:87,96`), independent of the dead `email-preferences-service.ts`.
